## Bazel Version

The project is configured to use Bazel version 8.7.0. If you are using
Bazelisk, then `.bazelversion` already configures the correct version.

## Build Image

Envoy defines the build images it expects for remote execution in
`.github/config.yml`. The repository generates the matching Bazel platform
configuration automatically.

For Hermetiq deployments that use the bb-worker-operator, the matching worker
pool example is
[`custom-values/rbeworkers/worker-envoy.yaml`](../custom-values/rbeworkers/worker-envoy.yaml).
Apply that worker after the Buildbarn chart has rendered the shared
`buildbarn-worker-config` ConfigMap.

Before running the Envoy build commands below, deploy the Envoy RBE worker pool
with at least 10 worker pods running. The example worker can autoscale from
zero, so raise the floor for an Envoy validation run and wait for the pods to
be ready:

```bash
kubectl apply -f custom-values/rbeworkers/worker-envoy.yaml
kubectl -n hermetiq patch rbeworker worker-envoy --type=merge \
  -p '{"spec":{"replicas":0,"autoscaling":{"minReplicas":10}}}'
kubectl -n hermetiq get pods | grep worker-envoy
```

Start the build only after at least 10 `worker-envoy` pods show `Running`.

## Project Configuration

Envoy can be built in several configurations. Details are documented in the
upstream `ci/README.md`. Configure Clang as the C/C++ compiler:

```text
--config=clang
```

Envoy's remote execution platform is generated by the repository. Select the
Linux x86_64 platform when using the Envoy worker pool:

```text
--extra_execution_platforms=//bazel/platforms/rbe:linux_x64
```

Hermetiq's Envoy worker pool does not support IPv6 test networking, so limit
Envoy's IP-version tests to IPv4:

```text
--test_env=ENVOY_IP_TEST_VERSIONS=v4only
```

### Hermetiq Configuration

Configure the Hermetiq Build Event Protocol (BEP) backend, remote cache, and
remote execution for Bazel as follows.

Replace the following placeholders with your Hermetiq account data.

- `$INSTANCE_NAME`: Your Project ID.
- `$CREDENTIAL_HELPER`: Path to your credential helper executable.
- `<your-domain>`: The `hosts.domainBase` you configured for the Hermetiq
  and Buildbarn charts. These examples assume both charts share one base
  domain, giving `bep.<your-domain>` (BEP), `bb.<your-domain>` (Buildbarn
  frontend gRPC), and `dashboard.<your-domain>` (web UI).

A convenient approach is to add a `build:hermetiq` config to `user.bazelrc` in
the Envoy checkout:

```bazelrc
build:hermetiq --config=clang
build:hermetiq --config=remote
build:hermetiq --bes_instance_name=$INSTANCE_NAME
build:hermetiq --bes_backend=grpcs://bep.<your-domain>
build:hermetiq --bes_timeout=120s
build:hermetiq --bes_results_url=https://dashboard.<your-domain>/build/
build:hermetiq --bes_upload_mode=wait_for_upload_complete

build:hermetiq --credential_helper="bep.<your-domain>=$CREDENTIAL_HELPER"
build:hermetiq --credential_helper="bb.<your-domain>=$CREDENTIAL_HELPER"

build:hermetiq --generate_json_trace_profile
build:hermetiq --experimental_profile_include_primary_output
build:hermetiq --experimental_profile_include_target_label
build:hermetiq --noslim_profile

build:hermetiq --remote_instance_name=$INSTANCE_NAME
build:hermetiq --remote_cache=grpcs://bb.<your-domain>
build:hermetiq --remote_executor=grpcs://bb.<your-domain>
build:hermetiq --extra_execution_platforms=//bazel/platforms/rbe:linux_x64
build:hermetiq --test_env=ENVOY_IP_TEST_VERSIONS=v4only
build:hermetiq --jobs=220
build:hermetiq --remote_retries=5
build:hermetiq --remote_retry_max_delay=30s
```

Keep Git build metadata on the command line so the shell expands it before
Bazel starts.

For large Linux workstations or builders, it is also useful to place Bazel's
output base, repository cache, and disk cache on a dedicated build disk:

```bazelrc
startup --output_base=/mnt/disks/data/bazel/output
build --repository_cache=/mnt/disks/data/bazel/repo_cache
build --disk_cache=/mnt/disks/data/bazel/disk_cache
```

### Build Targets

The following command runs some http tests using the Hermetiq config `--config=hermetiq`; excluded tests are currently known to fail
or require networking behavior that is not supported by the Envoy worker pool.

```bash
bazel test //test/common/... \
  --announce_rc \
  --config=hermetiq \
  --build_metadata="COMMIT_SHA=$(git rev-parse HEAD)" \
  --build_metadata="REPO=$(git config --get remote.origin.url)" \
  --build_metadata="BRANCH=$(git rev-parse --abbrev-ref HEAD)" \
  -- \
  -//test/common/http/http3:conn_pool_test \
  -//test/common/quic:envoy_quic_client_stream_test \
  -//test/common/quic:envoy_quic_utils_test \
  -//test/extensions/dynamic_modules/http:integration_test \
  -//test/extensions/filters/listener/original_dst:original_dst_integration_test
```

### Troubleshooting

If Envoy builds fail because Buildbarn cannot find a matching worker, inspect
the platform properties in the error. For example:

```text
ERROR: /mnt/disks/data/bazel/output/external/zlib-ng/BUILD.bazel:9:8: Executing genrule @@zlib-ng//:zconf_gen [for tool] failed: (Exit 34): FAILED_PRECONDITION: No workers exist for instance name prefix "223056c5-94bf-4ffc-baae-34eae027b99c" platform {"properties":[{"name":"container-image","value":"docker://gcr.io/envoy-ci/envoy-build@sha256:934b50777b1eb9348b0e62cafd9eee5c79828e57d4ca08083c86d3099b14bb42"},{"name":"dockerAddCapabilities","value":"SYS_PTRACE,NET_RAW,NET_ADMIN"},{"name":"dockerNetwork","value":"standard"},{"name":"dockerPrivileged","value":"True"}]}
```

This means Bazel requested an Envoy remote execution platform that no worker
currently advertises. Update the `container-image` platform property in the
Envoy worker config to use the SHA256 digest shown in the error, then reapply
the worker manifest.
